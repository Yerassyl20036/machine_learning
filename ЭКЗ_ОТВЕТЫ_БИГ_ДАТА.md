## БИЛЕТ №1
**1. Понятие Big Data и основные характеристики**

Big Data — совокупность подходов, инструментов и методов обработки структурированных и неструктурированных данных огромных объёмов для получения результатов, воспринимаемых человеком в условиях непрерывного прироста. Основные характеристики — модель **5V**:
- **Volume** (Объём) — терабайты и петабайты данных
- **Velocity** (Скорость) — высокая скорость генерации и обработки (потоки в реальном времени)
- **Variety** (Разнообразие) — структурированные (таблицы), полуструктурированные (JSON/XML), неструктурированные (видео, текст)
- **Veracity** (Достоверность) — неопределённость, шум, противоречивость данных
- **Value** (Ценность) — полезные инсайты после обработки

**2. Архитектура систем обработки больших данных**

Типовая архитектура включает:
- **Источники данных** — IoT, веб-логи, транзакции, соцсети
- **Ingestion layer** — Kafka, Flume (прием потоков)
- **Storage layer** — HDFS, S3, HBase, Cassandra
- **Processing layer** — Hadoop MapReduce, Apache Spark
- **Serving layer** — Hive, Impala, Presto (запросы)
- **Analytics / Visualization** — Superset, Grafana, Power BI

**3. Проблемы масштабирования и распределения данных**

- **Горизонтальное масштабирование** (scale-out) — добавление узлов vs **вертикальное** (scale-up) — улучшение одной машины. Для Big Data предпочтительно горизонтальное.
- **Шардинг** — разбиение данных на части по ключу (hash/range sharding)
- **Репликация** — дублирование данных на нескольких узлах для отказоустойчивости
- **Балансировка нагрузки** — равномерное распределение запросов
- Проблема **data skew** — неравномерное распределение данных между узлами снижает производительность
- **Network bottleneck** — узкое место при передаче больших объёмов между узлами

## БИЛЕТ №2
**1. Источники и типы больших данных**

Источники: социальные сети, IoT-устройства, транзакционные системы, веб-логи, мобильные приложения, медицинские записи, спутниковые снимки.

Типы по структуре:
- **Структурированные** — реляционные таблицы, CSV; легко запрашиваются через SQL
- **Полуструктурированные** — JSON, XML, Avro, Parquet; имеют схему, но гибкую
- **Неструктурированные** — текст, изображения, видео, аудио; ~80% всех данных в мире

**2. Методы хранения больших данных**

| Метод | Примеры | Применение |
|---|---|---|
| Распределённые ФС | HDFS, GlusterFS | Пакетная обработка |
| Объектное хранилище | Amazon S3, MinIO | Архивы, Data Lake |
| Колоночные БД | HBase, Cassandra | Быстрые записи/чтения по ключу |
| Документные БД | MongoDB, CouchDB | Гибкая схема |
| Реляционные MPP | Greenplum, Redshift | OLAP-аналитика |

**3. Выбор архитектуры хранения для распределённых систем**

Критерии: объём данных, тип запросов (OLTP vs OLAP), требования к задержке, частота обновлений, CAP-требования. Для аналитики с большими объёмами и редкими обновлениями — HDFS + Parquet. Для частых обновлений и ключевых запросов — HBase/Cassandra. Для гибкой схемы — MongoDB.

## БИЛЕТ №3
**1. Основные компоненты экосистемы Hadoop**

- **HDFS** — распределённая файловая система (NameNode + DataNodes)
- **YARN** (Yet Another Resource Negotiator) — менеджер ресурсов кластера
- **MapReduce** — движок пакетной обработки
- **Hive** — SQL-интерфейс поверх HDFS
- **HBase** — колоночная NoSQL БД поверх HDFS
- **Pig** — скриптовый язык для ETL
- **ZooKeeper** — координация распределённых сервисов
- **Sqoop** — импорт/экспорт данных из реляционных БД
- **Flume** — прием потоковых логов
- **Oozie** — планировщик рабочих процессов

**2. Принципы работы HDFS**

HDFS (Hadoop Distributed File System) основана на принципе **write-once-read-many**:
- **NameNode** — хранит метаданные (namespace, mapping файлов на блоки)
- **DataNode** — хранит реальные блоки данных (по умолчанию 128 МБ)
- **Репликация** — каждый блок реплицируется на 3 узла (rack-aware)
- **Heartbeat** — DataNode каждые 3 сек отправляет сигнал NameNode
- При отказе DataNode NameNode автоматически восстанавливает реплики
- Чтение: клиент запрашивает у NameNode местонахождение блоков → читает напрямую с DataNode

**3. Оптимизация отказоустойчивости в распределённых системах**

- **Репликация данных** (replication factor ≥ 3)
- **Rack-aware размещение** — реплики на разных стойках (rack)
- **Secondary NameNode / NameNode HA** с ZooKeeper для failover
- **Checkpoint** — периодическое сохранение состояния NameNode
- **DataNode automatic re-replication** при обнаружении потери блоков
- **RAID-подобные схемы** — Erasure Coding в HDFS 3.x (снижает накладные расходы репликации)

## БИЛЕТ №4
**1. Модель MapReduce и её назначение**

MapReduce — парадигма параллельной пакетной обработки данных, предложенная Google (Dean & Ghemawat, 2004). Назначение: разбить большую задачу на независимые подзадачи, выполнить их параллельно.

Фазы:
1. **Input Split** — данные разбиваются на порции
2. **Map(k1, v1) → list(k2, v2)** — маппер применяется к каждой записи независимо
3. **Shuffle & Sort** — промежуточные результаты сортируются и группируются по ключу
4. **Reduce(k2, list(v2)) → list(v3)** — редьюсер агрегирует значения по каждому ключу

Пример: подсчёт слов (WordCount) — Map выдаёт (слово, 1), Reduce суммирует.

**2. Принципы параллельной обработки данных**

- **Data parallelism** — одна операция выполняется над разными частями данных одновременно (MapReduce, Spark RDD)
- **Task parallelism** — разные задачи выполняются параллельно
- **Pipeline parallelism** — стадии обработки перекрываются
- Принцип **перемещения вычислений к данным** (move computation, not data) — задачи выполняются на узлах, где хранятся данные
- **Data locality** — YARN старается запустить задачу на том же узле, где блок данных

**3. Ограничения MapReduce в современных системах**

- Высокая задержка (latency) — не подходит для интерактивных запросов
- Каждая итерация пишет промежуточные результаты на диск (I/O bottleneck)
- Неэффективен для итеративных алгоритмов (ML: k-means, PageRank)
- Сложность написания нетривиальных пайплайнов
- YARN overhead для коротких задач
- Вытеснен Apache Spark, который работает in-memory и в 10-100x быстрее для итеративных задач

## БИЛЕТ №5
**1. Apache Spark и его особенности**

Apache Spark — унифицированный движок аналитики для больших данных с поддержкой in-memory вычислений. Особенности:
- **Unified API**: Spark SQL, Spark Streaming, MLlib, GraphX — в одной системе
- **RDD (Resilient Distributed Dataset)** — неизменяемые распределённые коллекции с lineage для восстановления
- **DataFrame / Dataset API** — высокоуровневый интерфейс с оптимизацией через Catalyst
- Языки: Scala, Python (PySpark), Java, R
- Интеграция с HDFS, S3, Kafka, HBase, Cassandra

**2. In-memory обработка данных**

Spark кэширует промежуточные данные в RAM вместо записи на диск (в отличие от MapReduce). Ключевые концепции:
- `df.cache()` / `df.persist(StorageLevel.MEMORY_AND_DISK)` — явное кэширование
- **Lazy evaluation** — преобразования (transformations) не выполняются до вызова action
- **DAG (Directed Acyclic Graph)** — Spark строит граф операций и оптимизирует план выполнения
- In-memory ускоряет итеративные алгоритмы ML в 10–100x по сравнению с MapReduce

**3. Оптимизация вычислений в Spark**

- **Partitioning** — правильный выбор числа партиций (`spark.sql.shuffle.partitions`)
- **Broadcast join** — для маленьких таблиц (< 10 МБ): `broadcast(smallDF)`
- **Predicate pushdown** — фильтрация до join/groupBy
- **Column pruning** — выборка только нужных столбцов (columnar formats: Parquet, ORC)
- **Избегать shuffle** — shuffle (wide transformations) дорог; использовать `repartition` vs `coalesce`
- **Tungsten execution engine** — byte-code generation, off-heap memory, cache-aware algorithms
- **Catalyst optimizer** — rule-based и cost-based оптимизация логических планов

## БИЛЕТ №6
**1. Потоковая обработка данных**

Потоковая обработка (stream processing) — обработка данных в режиме реального времени по мере их поступления, без ожидания накопления пакета. Характеристики: низкая задержка (миллисекунды–секунды), непрерывная обработка, stateful и stateless операции.

Примеры задач: мониторинг аномалий в реальном времени, fraud detection, агрегация метрик.

**2. Архитектура Apache Kafka**

Apache Kafka — распределённый брокер сообщений (event streaming platform):
- **Topic** — категория/поток сообщений
- **Partition** — каждый topic разбит на партиции; каждое сообщение имеет **offset**
- **Producer** — публикует сообщения в topic
- **Consumer / Consumer Group** — потребляет сообщения; каждая партиция обрабатывается ровно одним консьюмером в группе
- **Broker** — узел Kafka-кластера
- **ZooKeeper / KRaft** — координация кластера
- **Replication factor** — репликация партиций для отказоустойчивости
- **Retention** — сообщения хранятся заданное время (по умолчанию 7 дней)

**3. Обеспечение устойчивости потоковых систем**

- **Replication** — каждая партиция реплицируется (ISR — In-Sync Replicas)
- **At-least-once / exactly-once** семантика доставки
- **Idempotent producer** — предотвращает дубликаты при повторной отправке
- **Transactional API** — атомарные записи в несколько партиций
- **Consumer offset commit** — надёжная фиксация позиции чтения
- **Backpressure** — механизм регулировки скорости производителя и потребителя
- **Checkpointing** (в Spark Streaming / Flink) — сохранение состояния для восстановления

## БИЛЕТ №7
**1. NoSQL базы данных**

NoSQL (Not Only SQL) — класс СУБД, отказывающийся от реляционной модели в пользу гибкости, масштабируемости и производительности. Причины появления: огромные объёмы данных, горизонтальное масштабирование, гибкая схема, высокая скорость записи.

Общие черты: нет жёсткой схемы, горизонтальное масштабирование, eventual consistency (в большинстве случаев), BASE вместо ACID.

**2. Типы NoSQL систем**

| Тип | Примеры | Когда использовать |
|---|---|---|
| Key-Value | Redis, DynamoDB, Riak | Кэш, сессии, простые lookup |
| Document | MongoDB, CouchDB | Гибкие JSON-документы, каталоги |
| Column-family | Cassandra, HBase | Широкие таблицы, временные ряды, запись со временем |
| Graph | Neo4j, ArangoDB | Социальные сети, рекомендации, знания |
| Time-series | InfluxDB, TimescaleDB | IoT, метрики, логи |
| Search | Elasticsearch, Solr | Полнотекстовый поиск |

**3. Выбор NoSQL архитектуры под задачу**

- **Много записей, простые ключевые запросы** → Cassandra (partition key + clustering)
- **Сложные документы с вложенной структурой** → MongoDB
- **Граф связей** → Neo4j
- **Кэширование, счётчики** → Redis
- **Полнотекстовый поиск** → Elasticsearch
- **Временные ряды с высокой частотой** → InfluxDB
- **Big Data аналитика** → HBase поверх HDFS

## БИЛЕТ №8
**1. CAP-теорема**

CAP-теорема (Brewer, 2000) утверждает: распределённая система не может одновременно гарантировать все три свойства:
- **C (Consistency)** — все узлы видят одинаковые данные в любой момент
- **A (Availability)** — каждый запрос получает ответ (не обязательно актуальный)
- **P (Partition Tolerance)** — система продолжает работать при сетевых разделениях

Так как сетевые разделения неизбежны в реальных распределённых системах, выбор всегда между **CP** и **AP**.

**2. Консистентность и доступность данных**

- **Strong Consistency** (CP-системы): после записи все читают новые данные. HBase, ZooKeeper.
- **Eventual Consistency** (AP-системы): данные сойдутся к одному значению со временем. Cassandra, DynamoDB.
- **Read-Your-Writes**: клиент всегда читает свои записи
- **Monotonic Read**: каждое следующее чтение не старше предыдущего
- **Causal Consistency**: причинно-связанные операции видны в правильном порядке

**3. Компромиссы в распределённых системах**

PACELC-теорема расширяет CAP: даже при отсутствии разделения нужно выбирать между задержкой (L — Latency) и консистентностью (C).

Практические компромиссы:
- Cassandra: tunable consistency (`ONE`, `QUORUM`, `ALL`) — выбор между latency и consistency
- MongoDB с replicaSet: `readConcern: "majority"` для strong consistency, `"local"` для низкой задержки
- DynamoDB: `strongly consistent reads` дороже и медленнее eventual consistent reads

## БИЛЕТ №9
**1. Data Warehouse и его назначение**

Data Warehouse (DWH) — централизованное хранилище исторических данных, оптимизированное для аналитических запросов (OLAP). Характеристики (Inmon): subject-oriented, integrated, non-volatile, time-variant.

Архитектуры: **Star schema** (факты + измерения), **Snowflake schema** (нормализованные измерения). Примеры: Teradata, Amazon Redshift, Google BigQuery, Greenplum.

**2. Data Lake и его особенности**

Data Lake — хранилище сырых данных в нативном формате до трансформации. Особенности:
- **Schema-on-read** (vs schema-on-write в DWH)
- Все форматы: CSV, JSON, Parquet, изображения, видео
- Низкая стоимость хранения (HDFS, S3)
- Гибкость для исследовательского анализа и ML
- Риск превращения в **Data Swamp** без governance

**3. Проектирование гибридных хранилищ данных**

**Data Lakehouse** — архитектура объединяющая преимущества Lake и DWH:
- Открытые форматы: Apache Iceberg, Delta Lake, Apache Hudi
- ACID транзакции на объектном хранилище
- Schema enforcement + evolution
- Unified serving для BI и ML
- Примеры: Databricks Lakehouse, AWS Lake Formation, Azure Synapse

## БИЛЕТ №10
**1. ETL процессы**

ETL (Extract-Transform-Load) — процесс переноса данных из источников в целевое хранилище:
- **Extract** — извлечение из OLTP-систем, файлов, API
- **Transform** — очистка, нормализация, агрегация, обогащение
- **Load** — загрузка в DWH/Data Lake

Инструменты: Apache Spark, dbt, Talend, Informatica, Apache Airflow (оркестрация).

**2. ETL vs ELT подходы**

| | ETL | ELT |
|---|---|---|
| Порядок | Transform до загрузки | Load сначала, Transform в хранилище |
| Где трансформация | Промежуточный сервер | В самом хранилище (SQL) |
| Подходит для | Традиционные DWH | Облачные DWH (Redshift, BigQuery) |
| Производительность | Медленнее для больших объёмов | Использует мощь MPP |

**3. Оптимизация пайплайнов обработки данных**

- **Инкрементальная загрузка** — только delta-изменения (CDC — Change Data Capture)
- **Партиционирование** по дате — уменьшает scan при аналитических запросах
- **Колоночные форматы** — Parquet, ORC — в 5-10x быстрее CSV для аналитики
- **Параллелизация** — независимые задачи выполняются одновременно (Airflow DAG)
- **Мониторинг качества** — Great Expectations, dbt tests на каждом шаге
- **Кэширование** промежуточных результатов

## БИЛЕТ №11
**1. Batch обработка данных**

Batch processing — обработка накопленных данных большими пакетами по расписанию. Характеристики: высокая пропускная способность, высокая задержка (минуты–часы), подходит для ночных отчётов и трансформаций. Примеры: Hadoop MapReduce, Spark batch, SQL-запросы в DWH.

**2. Stream обработка данных**

Stream processing — обработка событий по мере поступления с минимальной задержкой. Характеристики: низкая задержка (миллисекунды–секунды), непрерывность, stateful операции.

Инструменты: **Apache Kafka Streams**, **Apache Flink** (true streaming, event-time), **Spark Structured Streaming** (micro-batch), **Apache Storm**.

Ключевые концепции: **event time vs processing time**, **watermarks** (граница ожидания опоздавших событий), **windows** (tumbling, sliding, session).

**3. Интеграция batch и stream подходов**

**Lambda-архитектура**: batch layer (точные исторические результаты) + speed layer (приближённые результаты в реальном времени) + serving layer.

**Kappa-архитектура**: только stream layer — вся история переигрывается при необходимости.

**Unified batch+stream**: Apache Flink и Apache Beam предоставляют единый API для обоих режимов. Spark Structured Streaming позволяет использовать одинаковый код для batch и streaming.

## БИЛЕТ №12
**1. Lambda архитектура**

Lambda архитектура (Nathan Marz) — архитектурный паттерн для систем обработки больших данных:
- **Batch layer** — хранит полный immutable dataset, периодически пересчитывает batch views
- **Speed layer** — обрабатывает только свежие данные в реальном времени, compensates задержку batch layer
- **Serving layer** — объединяет batch views и real-time views для ответа на запросы

**2. Компоненты Lambda**

- **Batch layer**: HDFS/S3 + Spark/Hadoop MapReduce → batch views в Hive/HBase
- **Speed layer**: Kafka → Spark Streaming/Flink → real-time views в Redis/HBase
- **Serving layer**: Impala/Presto объединяет оба слоя, отвечает на запросы

**3. Ограничения Lambda архитектуры**

- Дублирование логики: одну и ту же трансформацию нужно реализовывать дважды (batch + stream)
- Сложность поддержки и синхронизации двух кодовых баз
- Высокая операционная сложность
- Задержка batch layer (часы) означает что real-time данные не верифицированы
- Решение: **Kappa архитектура** или **Lakehouse с streaming ingestion**

## БИЛЕТ №13
**1. Kappa архитектура**

Kappa архитектура (Jay Kreps, LinkedIn, 2014) — упрощение Lambda: убрать batch layer. Все данные обрабатываются через единый streaming pipeline.

Ключевая идея: лог событий (Kafka) хранится достаточно долго; при необходимости пересчёта старых данных — запускается новый streaming job с начала лога с новым consumer group id.

**2. Принципы потоковой обработки**

- **Event sourcing** — система состоит из неизменного лога событий
- **Immutability** — события не удаляются, только добавляются
- **Replayability** — любой computation можно воспроизвести с любого offset
- **Stateful processing** — агрегации сохраняются в RocksDB (Flink) или состоянии Spark
- **Exactly-once semantics** — каждое событие обработано ровно один раз

**3. Сравнение Lambda и Kappa**

| | Lambda | Kappa |
|---|---|---|
| Слои | batch + speed + serving | только streaming |
| Сложность кода | Высокая (дублирование) | Низкая |
| Точность | Batch layer точнее | Зависит от реализации |
| Задержка | Низкая через speed layer | Низкая |
| Перепроцессинг | Сложно | Просто (replay) |
| Применение | Разные требования к точности | Единая логика обработки |

## БИЛЕТ №14
**1. Распределённые вычисления**

Распределённые вычисления — модель, в которой задача выполняется несколькими компьютерами (узлами), обменивающимися сообщениями по сети. Принципы: нет общей памяти, асинхронность, возможность частичных отказов.

Модели: **Message Passing** (MPI), **Shared-Nothing** (каждый узел независим, своё хранилище), **Actor Model** (Akka), **MapReduce/Spark**.

**2. Параллелизм в обработке данных**

- **Data parallelism** — разбить данные, применить одну операцию параллельно (MapReduce, Spark partitions)
- **Pipeline parallelism** — стадии обработки перекрываются по времени
- **Task parallelism** — независимые задачи выполняются одновременно (Airflow DAG)
- **SIMD** — уровень процессора (Vectorized execution в Arrow, Spark Tungsten)
- Метрика: **speedup = T_serial / T_parallel** (закон Амдала ограничивает максимальный ускорение)

**3. Балансировка нагрузки в кластерах**

- **YARN ResourceManager** — выделяет CPU/RAM контейнеры задачам
- **Consistent Hashing** — равномерное распределение ключей по узлам с минимальной перебалансировкой при изменении кластера
- **Work stealing** — незагруженный воркер забирает задачи от перегруженного
- **Dynamic resource allocation** (Spark) — исполнители добавляются/удаляются по нагрузке
- **Fair Scheduler / Capacity Scheduler** (YARN) — справедливое распределение между очередями

## БИЛЕТ №15
**1. Индексация данных**

Индекс — структура данных, ускоряющая поиск ценой дополнительного места и времени на запись. Типы:
- **B-Tree** — стандартный индекс для диапазонных запросов (RDBMS)
- **Hash index** — точный поиск по ключу (O(1))
- **Inverted index** — полнотекстовый поиск: слово → список документов
- **Bitmap index** — для категориальных данных с малым числом значений
- **LSM-tree** (Log-Structured Merge-tree) — оптимизирован для записи (HBase, Cassandra, RocksDB)

**2. Поисковые системы**

Поисковые системы для Big Data обеспечивают полнотекстовый поиск и аналитику в реальном времени. Этапы: **tokenization → normalization → stemming → inverted index**.

TF-IDF (Term Frequency-Inverse Document Frequency): $score(t,d) = tf(t,d) \cdot \log\frac{N}{df(t)}$ — базовая метрика релевантности.

**3. Применение Elasticsearch**

Elasticsearch — распределённая поисковая система (Apache Lucene под капотом):
- **Index** — аналог БД; **Document** — JSON-запись; **Shard** — единица распределения
- Horizontal scaling: shards распределяются по узлам
- **Full-text search** с fuzzy matching, boosting, highlights
- **Aggregations** — аналог GROUP BY для аналитики в реальном времени
- **ELK Stack**: Elasticsearch + Logstash (ingestion) + Kibana (визуализация)
- Применения: логи, мониторинг, e-commerce поиск, аналитика

## БИЛЕТ №16
**1. Качество данных**

Качество данных — степень соответствия данных требованиям конкретной задачи. Измерения качества:
- **Accuracy** (Точность) — данные соответствуют реальному миру

**3. Управление качеством данных в Big Data**

- **Data lineage** — отслеживание происхождения данных

## БИЛЕТ №23
**1. Графовые базы данных**

Графовые БД хранят данные в виде **узлов (nodes)** и **рёбер (edges)** с свойствами. Оптимальны для данных с плотными связями.

Примеры: **Neo4j** (Cypher query language), **Amazon Neptune**, **ArangoDB** (multi-model), **JanusGraph** (distributed).

Запрос в Cypher (Neo4j): `MATCH (a:Person)-[:KNOWS]->(b:Person) WHERE a.name='Alice' RETURN b.name`

**2. Моделирование связей**

- **Property Graph** — узлы и рёбра имеют свойства (key-value)
- **RDF (Resource Description Framework)** — тройки subject-predicate-object (для knowledge graphs)
- Паттерны: **социальный граф** (Person -KNOWS→ Person), **граф знаний** (Entity -relation→ Entity), **граф зависимостей** (Package -DEPENDS_ON→ Package)
- **Schema-optional** — нет жёсткой схемы, граф эволюционирует естественно

**3. Применение графовых алгоритмов**

- **PageRank** — ранжирование узлов по входящим связям (веб-поиск, влиятельные люди)
- **Shortest Path** (Dijkstra, BFS) — навигация, маршрутизация
- **Community Detection** (Louvain, Label Propagation) — сегментация аудитории
- **Connected Components** — выявление изолированных групп
- **Centrality** (Betweenness, Closeness) — поиск ключевых узлов в сети
- Инструменты: **GraphX** (Spark), **Neo4j GDS** (Graph Data Science Library), **NetworkX** (Python)

## БИЛЕТ №25
**1. Управление производительностью**

Производительность распределённой системы определяется: **throughput** (пропускная способность), **latency** (задержка), **scalability** (масштабируемость). Метрики: RPS, p50/p95/p99 latency, CPU/Memory utilization.

**2. Оптимизация обработки данных**

- **Spark**: увеличить parallelism (spark.default.parallelism = 2-3x число ядер), avoid UDFs (использовать встроенные функции), использовать Parquet + column pruning
- **Kafka**: увеличить число партиций для больший throughput, настроить batch.size и linger.ms у producer
- **HDFS**: block size 128-256 МБ для больших файлов, short-circuit reads
- **Query optimization**: избегать full-table scan, использовать partition pruning, push predicates вниз
- **Caching**: кэшировать часто используемые датасеты (Spark `cache()`, Redis для lookup таблиц)
- **Compaction**: объединять мелкие файлы (small files problem в HDFS)

**3. Мониторинг распределённых систем**

- **Метрики**: Prometheus + Grafana — сбор и визуализация числовых метрик
- **Логи**: ELK Stack (Elasticsearch + Logstash + Kibana) или Loki + Grafana
- **Трейсинг**: Jaeger, Zipkin — distributed tracing для отладки latency
- **Alerting**: Alertmanager (Prometheus), PagerDuty — автоматические оповещения
- **JMX** — Java Management Extensions для Kafka, HBase метрик
- **Spark UI** (port 4040) — DAG визуализация, стадии, задачи, shuffle read/write

- **Apache Kafka Streams** — Java-библиотека, работает внутри приложения, нет отдельного кластера
- **Apache Flink** — true streaming (event-by-event), сильная state management, exactly-once, event-time processing
- **Spark Structured Streaming** — micro-batch (по умолчанию), continuous mode, DataFrame API
- **Apache Storm** — ранний streaming, low latency, at-least-once
- **Google Cloud Dataflow** — managed Apache Beam, auto-scaling
- Сравнение latency: Storm < Flink < Spark Streaming

**3. Надёжность потоковых архитектур**

- **Checkpointing** — периодическое сохранение состояния (Flink каждые N сек)
- **Savepoints** — ручные снимки состояния для rolling upgrade
- **Exactly-once semantics** — через distributed snapshots (Chandy-Lamport algorithm в Flink)
- **Dead letter queue (DLQ)** — некорректные сообщения отправляются в отдельный topic
- **Circuit Breaker** — остановка обработки при критических ошибках downstream
- **Backpressure** — потребитель сигнализирует производителю о перегрузке

## БИЛЕТ №28
**1. Методы сжатия данных**

Сжатие снижает объём хранения и ускоряет I/O. Типы:
- **Lossless**: данные восстанавливаются точно
  - **Snappy** — быстрое сжатие/распаковка, умеренный коэффициент (2x); используется в Parquet по умолчанию
  - **Gzip** — высокий коэффициент (5-10x), медленнее; для холодных данных
  - **LZ4** — очень быстрая распаковка; для in-memory (Spark)
  - **Zstandard (ZSTD)** — баланс скорости и степени сжатия
- **Lossy** (не для аналитических данных) — JPEG, MP3 — для медиа

Колоночные форматы (Parquet, ORC) + columnar encoding (RLE, dictionary) + сжатие → 10-50x уменьшение vs CSV.

**2. Хранение больших объёмов информации**

- **Tiered storage**: Hot (SSD/RAM) → Warm (HDD) → Cold (S3/Glacier) — автоматическое перемещение по времени доступа
- **Columnar formats**: Parquet, ORC — эффективны для аналитических запросов (column pruning, vectorized reads)
- **Erasure Coding** (HDFS 3.x) — вместо 3x репликации: 1.5x overhead при той же отказоустойчивости (Reed-Solomon codes)
- **Deduplication** — дедупликация на уровне блоков (ZFS, NetApp)
- **Object storage** (S3, MinIO) — бесконечно масштабируется горизонтально

**3. Оптимизация использования ресурсов**

- **Partition pruning** — запрос только нужных партиций (partition by date)
- **Z-ordering/Clustering** (Delta Lake) — физическая сортировка данных для данных с частой фильтрацией
- **Compaction** — слияние мелких файлов в большие (OPTIMIZE в Delta Lake)
- **Vacuuming** — удаление устаревших файлов
- **Resource queues** (YARN Capacity Scheduler) — квоты на ресурсы для разных команд
- **Spot instances** для batch workloads — снижение затрат на 70-90%

## БИЛЕТ №30
**1. Ограничения технологий Big Data**

- **Сложность** — экосистема Hadoop/Spark требует специализированных знаний
- **Задержка** — batch-системы не подходят для real-time (< секунды)
- **Малые данные** — для небольших датасетов обычный SQL эффективнее
- **ACID-транзакции** — традиционно сложны в распределённых системах (улучшается в Lakehouse)
- **Vendor lock-in** — зависимость от облачных провайдеров
- **Стоимость** — высокие расходы на инфраструктуру и специалистов

**2. Проблемы обработки данных**

- **Data skew** — неравномерное распределение данных по партициям снижает производительность
- **Small files problem** — тысячи мелких файлов в HDFS перегружают NameNode
- **Schema evolution** — изменение схемы может сломать downstream пайплайны
- **Late data** — опоздавшие события нарушают агрегации в потоковых системах
- **Cold start** — кластер требует времени для выхода на мощность
- **Debugging** — отладка распределённых систем сложнее монолитных

**3. Этические и правовые аспекты**

- **GDPR** (EU) — право на забвение, минимизация данных, согласие на обработку, штрафы до 4% годового оборота
- **PDPL** (Казахстан) — Закон о персональных данных, локализация данных казахстанцев
- **Алгоритмическая предвзятость** — ML-модели воспроизводят и усиливают существующие bias (дискриминация при найме, кредитовании)
- **Прозрачность** — право объяснения автоматических решений (GDPR Art. 22)
- **Data sovereignty** — право государств контролировать данные своих граждан
- **Ownership** — кому принадлежат данные пользователей?
- **Surveillance capitalism** — монетизация поведенческих данных без полного осознания пользователями
